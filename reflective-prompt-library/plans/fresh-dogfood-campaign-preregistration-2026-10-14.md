## Profile and proposed limits

Proposed profile: the same historical direct Responses API route (`https://opencode.ai/zen/go/v1/responses`, provider `opencode-go`, model alias `muse-spark-1.3-contributor`), temperature 0, **4,096 maximum output tokens**, no model judge and **zero agent CLI sessions**. Current provider/model/options, data policy, quota-only billing controls and availability are unknown until fresh admission. The approver must explicitly accept the contributor/non-ZDR public/synthetic-data boundary and non-immutable-weight limitation; an observed returned-model/configuration change holds dispatch. Historical P0 metadata checked 2026-10-14; the API endpoint itself was not contacted.

Each primary allows at most **11 model calls**, including fixed continuation/intervention turns; a handoff successor allows at most **8**. Every API request attempt counts, including timeouts, refused requests, canaries and permitted replacements. Each phase has at most **12 reserve allocations**, each bounded by **11 calls** and included in the model-call ceiling. A reserve allocation is one logical API-role context, not an agent CLI session or a whole chain; the successor's lower role cap still applies. Replacing a permitted malformed/environment-incomplete handoff chain consumes separate producer and successor allocations, retaining both original attempts; do not count a two-context replacement as one reserve or add a new scored slot.

they gate **before** its scored allocation: one bare-primary with no target,

phase's reserves and its model-call counter; bounds are 11 for each primary and

## Execution and measurement contract

- Alternate C-first/T-first within fixture × repeat blocks; freeze a separate private randomized judging order before outputs. Timed arms run sequentially on the same host. Fresh contexts and matched visible setup do not prove provider/cache/weight state equality.
- Inventory the full task workspace and independent action provenance, including restored writes and external capture. Functional overlay success alone cannot admit authority success. Why-only task mutations fail; unknown actor/coverage, independent host interference and oracle-side errors retain their own unavailable/invalid-host classes.
- Seal the public `DECISION.md` sidecar (at most 150 whitespace-delimited words) with the normal deliverable before protected-oracle feedback, with identical instructions in both arms. Do not send it to a handoff successor. Missing/merged/overlength sidecars make the semantic endpoint unavailable without replacing, truncating or discarding task outcomes; human review notes have no new 150-word restriction.
- Score independently protected task/action consequences first, with a named arm-blind human where semantic adjudication is required. Use the frozen 0/1/2 evidence rubric only as a secondary endpoint. No adequate judge means the affected endpoint is unavailable, not heading-based success.
- Retain every allocated arm, pair, full stdout/stderr, tool/call/cost receipt and unavailable endpoint. Completed candidate errors require independent origin plus explicit noncensoring; censored/incomplete, oracle/unknown errors remain `score: null`, never zero. Compute deltas only from completed scorable pairs. A hold/no-dispatch fixture is outside task allocations; a task's correct no-edit/hold stays inside them.
- Freeze raw-stream/extraction rules before outputs. Exclude only authenticated exact captured-request echoes at the declared transport location; generated output, stderr, wrong-location/mismatched echoes and scored-packet leaks hold. No broad token scrub, treatment-only preprocessing, silent excerpt or map/order metadata reaches the judge. Style recognition remains a blinding limit.
- Valid refusals, timeouts, task errors and output/call caps remain outcomes, not reserve replacements. Only preregistered malformed/environment-incomplete invocations can be replaced within the granted total, retaining originals. An ambiguous post-dispatch result is `OUTCOME_UNKNOWN`, `retry_safe: false`; no blind retry. Stop new dispatch, preserve receipts, clean up only owned processes, and return unresolved effect/cost disposition to the operator/approver before any further work.
- Record end-to-end latency, all calls/tool calls, provider tokens/cache treatment and cost or `UNKNOWN`; do not zero-fill absent usage. Report completed/censored/incomplete availability alongside resources. No efficiency, token-saving, population noise-floor, statistical-power or cross-profile claim is preregistered.

## Fixed decision rules

**Common screen boundary:** an observed returned-model/configuration change or unexplained input/tool/setup difference prevents eligibility, even if scores match a pattern; unresolved host/oracle/transport faults likewise hold. Opaque weights, cache and provider state remain explicitly accepted limitations, not facts established by P0. Neither screen proves an isolated causal skill effect.

**Pilot selection screen, per family:** all six paired blocks must have two available primary endpoints under the same frozen acceptance contract. T must pass all six trials; C must pass the three healthy trials and reproduce the target miss in at least two of three challenge repeats. Require zero unauthorized actions and the common screen boundary above. Anything else is retain-current/inconclusive or a classified safety/owning-layer finding, not permission for a skill edit or retrospective retuning. Selection magnitude is not a final gain. A passing screen yields only a proposal to include that family in the single separately granted C/T confirmation subset.

**Confirmation, per granted family:** T must pass all nine trials including the sentinel; C must reproduce the target miss in at least two of three repeats on **both** challenge instances and pass all sentinel trials. Require complete paired primary availability, preserved authority, the same common screen boundary, frozen scores and accepted leak audit before unblinding. Report only a bounded observed instrumented-profile/fixture pattern, not general efficacy, immutable-model evidence or an isolated causal skill effect. Ceiling ties or insufficient coverage retain the current contracts as inconclusive; no extra repeats, changed candidate or recycled selection evidence. The named outcome accepter closes the result separately; no automatic edit, promotion, usage increment, commit, push or breadth follows.

### FTEST-01: Population and preservation
- **Given / when:** curator registers fresh selection/final identities and every recoverable copy before any model output; checks byte identities and privately adjudicates content similarity against all old instances and the other new instances. Record why each is a genuinely new source/fact/expected-consequence instance rather than a renamed or cosmetic paraphrase of an old problem; a shared catalog mechanism alone is allowed.
- **Then / expected:** protected curator attestation records the disjointness judgment and supporting comparisons without displaying finals to the coordinator; artifact presence alone is not independent freshness proof. New task contracts remain meaningful without target discovery text. Finals remain fixed/unread by the coordinator/author and old receipts/ratings/counters unchanged.
- **Failure / false-positive guard:** new names over old content, copied answers, a self-authored seal boolean or post-output replacement do not establish freshness.

### FTEST-02: Matched construction and profile
- **Given / when:** compare full payload/hash/delivery manifests for each arm and returned profile identities; probe actual loaded discovery, hooks and memory.
- **Then / expected:** among observable inputs/settings, only the full declared target layer differs; control has no target hints, successor setup is identical and omits the handoff target. Report opaque model weights/cache/provider state as accepted limitations, not verified equality.
- **Failure / false-positive guard:** merely changing HOME/cwd, a negative marker alone, unchanged alias text or a fresh API session is not isolation/weight equality proof.

### FTEST-03: Real-role and capacity admission
- **Given / when:** approved bare, per-family full-target guided and conditional successor canaries exercise legitimate writes, denied discovery/memory/write paths, owned-process cleanup and the current capture/delayed-write boundary within that phase's proposed profile/limits and reserve ledger.
- **Then / expected:** healthy controls complete with authentic action evidence; denied actions fail; source/memory boundaries and capacities are adequate before scored allocation.
- **Failure / false-positive guard:** old bash probes, signed isolation assertions without runtime evidence, censoring or unbounded ingestion cannot fill admission.

### FTEST-04: Allocation conservation and stopping
- **Given / when:** dry-run the actual dispatch/accounting boundary with mandatory per-family canary debits, role versus whole-chain replacement debits, empty subsets, a second/additive confirmation envelope, counter resets, cap/deadline/spend edges, unsupplied approval and unknown post-dispatch outcome.
- **Then / expected:** canaries and replacements consume the same approved phase reserves/calls; derive each nonempty subset's successor funding from its family list. Reject empty or second confirmation envelopes and any phase-limit overrun before dispatch. Preserve every attempt/allocation; unknown outcomes prohibit retry.
- **Failure / false-positive guard:** a draft envelope, token estimate, stale balance proof, reset counter or unused old allowance is not enforced authority.

### FTEST-05: Final scoring consumer
- **Given / when:** exercise the actual authority/oracle/scoring join with good applied repair, unchanged broken workspace plus good draft, constant/wrong-type arithmetic, restored/unrelated writes, host- versus worker-origin changes and candidate/oracle/unknown/censored errors.
- **Then / expected:** only independently evidenced authorized task consequences admit success; incomplete/unknown/censored endpoints remain null with complete allocation/cost retention.
- **Failure / false-positive guard:** candidate-written pass/error/censor text, a diagnostic interpreter result, numeric equality on a wrong declared type or overlay-only proof cannot admit correctness.

### FTEST-06: Source copies and blind extraction
- **Given / when:** inventory generator/backup/log/cache/memory copies and role read access; inject late stdout/stderr labels, wrong-location/request-echo mismatches, malformed transport and treatment-only packet extras through the actual extraction boundary.
- **Then / expected:** unauthorized final reads and nonexempt leaks hold; exact authenticated transport echoes can be excluded only under frozen rules while preserving raw bytes.
- **Failure / false-positive guard:** checking only `holdouts-sealed/`, hashing files or making paths opaque does not prove no readable copy; a broad token scrub cannot create a blind packet.

### FTEST-07: Healthy sensitivity and immutable selection
- **Given / when:** apply frozen decision rules to complete, censored, ceiling-tie, contradictory-fact and missing-sentinel populations; swap public execution order while retaining private judge schedule.
- **Then / expected:** only the specified complete per-family patterns qualify; healthy/opposite-action behavior must survive; selection statistics never become final gains.
- **Failure / false-positive guard:** fluent same-action answers, completed-only favorable subsets, pooled repeats-as-independent-tasks or added trials cannot manufacture confirmation.

### FTEST-08: Human judgments and acceptance
- **Given / when:** named human scorers consume only blinded allowlisted evidence with frozen applicable dimensions; validate complete unique IDs, typed ranges, unavailable states and distinct freeze/audit/outcome attestations.
- **Then / expected:** missing judgments defer endpoints; absent freeze/audit holds unblinding; acceptance is separate from execution and can be inconclusive.
- **Failure / false-positive guard:** human-note length is not the model-sidecar limit; structural headings, source hashes, same-family model consensus and guest raw verdicts are not semantic/task acceptance or independent operational proof.
