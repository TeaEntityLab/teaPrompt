> **Status: proposed, planning-only — 2026-10-06.** Spec version RSD-2. User request: "according to evidences how could I design runtime skills? plan as possible". This is a non-authoritative design, not an adoption decision, implementation authorization, host-enforcement claim or checkpoint verdict. English is canonical for this artifact. Existing skill contracts and `06-repo/AGENTS.md` retain authority. RSD-1's draft pilot accounting is superseded before any operational handoff; no runtime artifact or oracle was instantiated against it.

## 1. Goal, scope and readiness

**Recommendation:** design runtime-aware skills as task-scoped generators of executable artifacts and explicit host contracts, not as a second runtime. The model proposes content; deterministic scripts control known sequencing; the existing host owns permissions, process lifetime, budgets, actual observations and any durable state; the named product/human owner closes acceptance.

- **Intended outcome:** a user can select the smallest sufficient skill, generate a bounded inspectable workflow, see why a gate holds, and distinguish verified output from accepted delivery.
- **Selected formalization:** L3 — skill + artifacts + deterministic verifier/gate. A prompt/checklist is sufficient for a single attended call without workflow state. Host L4 capabilities are conditional requirements, not capabilities supplied by this design. Formalization L0–L4 is not Strictness L1–L6; this planning review uses Strictness L4.
- **In scope:** interfaces and responsibilities for the five existing registered packs; an evidence/acceptance matrix; usage-first scenarios; phased host/model experiments; permission and promotion boundaries.
- **Out of scope:** runtime implementation, a new core skill/pack, pack merge, scheduler, generic adapter, recorder, broker, cancellation manager, deployment, billing/settings changes, authoritative-oracle edits, or new usage/recurrence/checkpoint rulings.
- **Planning approval is not implementation authorization.** A later run needs explicit task/run authorization; unattended/effectful work needs signed intent and its approved envelope. Changing TeaPrompt's standing non-goal needs the existing owner-sentence/reproduced-defect process, not approval of this document.
- **Definition of Ready for an actual pilot:** named task/root, human/spec owner, current spec and independent oracle, actual CLI/model/profile, task-declared required controls/freshness, permitted writes/sinks, host-enforced time/cost/call limits, evidence owner and acceptance owner. Model arms additionally need configured-provider usage credits. Until these exist, the relevant experiment is blocked; the design can still be completed.

Authority: [harness policy](../06-repo/AGENTS.md), [Standing Non-Goals and lessons](../PROJECT_KNOWLEDGE.md), [MR rulings](methodology-only-rethink-panel-2026-10-01.md), [product/runtime ownership](product-runtime-ownership-panel-2026-08-25.md). This request authorizes planning, not revision of those decisions.

## 4. Minimal runtime-aware skill interface

Use the existing Module Contract and emitted records rather than a new universal schema. For each task instantiate:

1. **Trigger and result:** the real repeated/control-flow problem, product-visible outcome, independent completion check, scope and non-goals. Route ambiguous intent to brief/spec, not an agent loop.
2. **Ownership:** proposer, authorizer, effect executor and acceptance owner; one host lifecycle owner; plus three approval-class roles that must each resolve to a named non-model party at instantiation — artifact owner (approves the generated artifact set), host authorizer (asserts run authorization), attester/host verifier (permits acceptance review). A single named host may fill multiple roles only when the task declares that concentration explicitly; the model is never the sole authorizer or accepter, and never the artifact owner of the packet that governs it. Gate selection (whether a task requires a PREFLIGHT) is the artifact owner's decision, recorded in the packet.
3. **Reviewed execution:** actual task-root cwd, stdin-capable AGENT_CMD/wrapper and observed command/version/profile. Prompts go through stdin, not argv. Do not copy historical CLI flags as a promise about a current version.
4. **Protection and evidence:** immutable inputs/oracles/verifiers/control records, host write exclusions and task-specific observed controls. Missing required evidence is unknown/hold. Hashes protect bindings only when their owner and the runtime protection are established separately.
5. **Bounds:** template-specific caps plus the host's actual time/cost/process enforcement. Nested composition declares one total budget and passes remaining budget downward; multiplying per-layer caps without a shared bound is not a bounded run. A step cap alone does not stop a hung child.
6. **Release:** one selected executable PREFLIGHT pathname when required; named deterministic verifier over the actual merged/final artifact. Empty PREFLIGHT is an attended example with no enforcement claim, never `met`.
7. **Failure and handoff:** preserve raw output, per-stage artifacts and cause; distinguish hold/stale, cap, content stall, execution error and ambiguous effect. Missing acceptance stops and repairs the packet. Do not return unverified last output as success.
8. **Acceptance and maintenance:** current spec/host/oracle bindings and named accepter; rerun affected behavioral surfaces after a substantive change, not to reconfirm unchanged historical success. Preserve failed harness attempts with their original classification.

### Existing finite-checker records

The binding is exactly the existing mapping: `spec_version`, `host_identity`, `required_preconditions`, task-declared finite `max_age_seconds`, `files` (path → SHA-256). The JSON run note carries `spec_version`, `host_identity`, all five explicit controls, `evidence`, and `status: artifact-complete`. Controls are `oracle_sealing`, `sink_isolation`, `budget_enforcement`, `durable_ledger_storage`, `human_decision_channel`; every default is `unknown`.

Evidence rows reuse `precondition`, `result`, `spec_version`, `host_identity`, timezone-qualified `observed_at`, `command` (data), `principal`, `exit_code`, and `artifacts` (path/hash). Every `met`, including an optional claim, needs coherent evidence. The complete probe must succeed and include the intended denial plus positive controls; a denial exit by itself is not a met result. Only known unique controls, regular file sources and coherent fresh bindings are admissible.

Verified command interface: `python3 checks/preflight.py run-note.json binding.json`. In a generated flow, select the host-protected absolute path to `checks/run-preflight.sh`; it supplies those arguments. The checker emits `ready`/0 or `hold`/`stale`/4. `ready` neither authenticates the producer nor upgrades `artifact-complete` to `enforcement-proven`.

**No new attestation field, signing service or privileged probe executor goes inside this checker.** The host obtains actual observations under the actual role, protects evidence/binding/checker from worker writes, and decides whether its required operational preconditions are met. A syntactically valid principal string is not role identity. E8 demonstrates this boundary directly.

## 5. Workflow, ownership and release

This is a table for generated task contracts, not a new executable state machine or universal lifecycle enum. The canonical governed gates remain in governed-delivery.

| Stage | Type / inputs | Owner and action | Outputs | Next transition / control owner | Gate | Failure and recovery |
| --- | --- | --- | --- | --- | --- | --- |
| Intent and spec | Human + current goal/oracles | Named human signs intent; spec owner fixes current version and unknown owners | Intent, spec, oracle manifest | Human/spec owner allows generation | Signed intent for governed work; measurable acceptance | Missing/unsigned intent or acceptance → hold, stop_and_repair; no model release |
| Generate minimal artifacts | Model + approved task shape | Selected skill emits only the needed packet, prompts and topology/loop | Current packet, script, checks, envelope as needed | Artifact owner approves instantiation | Sources complete; interfaces/caps/oracle ownership explicit | Missing criterion or protocol → stop_and_repair; a parsed artifact is not enforced |
| Observe host controls | Host data/action + actual role/profile | Host owner executes safe positive/refusal controls and protects actual records | Run note, binding, raw observations | Host authorizer determines actual preconditions | Exact role, scoped positive/denial results, approved envelope | Required control unmet/unknown → hold; no wiring or role proof is inferred from strings |
| Finite preflight | Deterministic data check | Host-selected protected executable checks coherent fresh required records | Per-stage preflight output | Script allows dispatch only after exit 0 and run-level authorization already asserted | Executable pathname; current bindings | Missing/non-executable/failing selection → exit 4; stale → spec/host re-observation and re-plan |
| Bounded proposal/work | LLM or approved host action + current packet | Worker proposes/content-generates within host-granted rights; host/broker owns any privileged effect | Per-stage files, raw CLI output, ledger | Deterministic script controls the next stage | Actual remaining budget, permissions; preflight before each dispatch | Out-of-envelope, repeated failure or boundary attempt → stop/escalate; driver exit alone is not canceled |
| Pre-release verification | Deterministic verifier + current candidate | Protected preflight runs after work; named verifier checks actual final/merged output | Verification and evidence records | Attester/host verifier permits acceptance review | Host/spec/oracle current; final result verified; holds dominate quorum | Hold/stale blocks release, merge, retirement and zero-call success; unverified cap output never succeeds |
| Named acceptance | Human/product action + product evidence | Named accepter validates current product preconditions and closes delivery | Acceptance record; canonical commit evidence only when applicable | Named accepter, never executing model | All applicable oracles and host/product conditions | Execution-complete ≠ accepted; stale proposal or unsigned decision remains unaccepted |
| Retro | Artifact/data + actual receipts | Retro owner records fired/bypassed gates and outcomes | Scoped lessons and improvement candidates | Owner may propose later policy change | Provenance and evidence classes retained | Policy change does not activate policy or affect in-flight leases |

Run-level authorization is asserted once by the named host authorizer before the generated script starts (the intent/envelope approval), and is consumed as a start condition — it is not a per-dispatch artifact the schema could carry, and `ready` alone never authorizes dispatch. Boundary attempts have no detector inside the script: the host owner reviews its own denial/audit log during the Observe-host-controls and acceptance stages; a worker that silently hits a denied path and exits 0 produces no escalation artifact, so attempt detection is declared a host-side duty, not a generated-script guarantee.

## Falsifiability

Name one outcome that would falsify this design, then route the result to the named owner rather than repairing the plan in place:

- A fresh task instantiation cannot name its product result, independent oracle, required permissions, host owner or accepter.
- A selected missing/non-executable/failing gate dispatches first work or releases an already-verified result.
- An unknown/stale required record permits the normal path, or a worker-written/invented coherent record releases a protected host operation.
- A promised cancel/recovery/effect case cannot satisfy its declared fault boundary on the actual host.
- A no-skill control arm wins while preserving the same host safety floor and a blinded deterministic scorer; report the narrow per-case result, not general skill failure.
- A narrower analogue is reported as a complete current GDR campaign, or this planning document is cited as runtime/adoption/recurrence approval.

A mid-run spec bump marks **plan items, ledger entries, oracle manifest, task packet and acceptance record** stale; return to spec re-validation and affected-slice re-planning before downstream work. A finite checker noticing one stale binding is not proof this full transition exists. Checker dispositions, seven delivery gates and proposal/control-decision states are separate concepts; do not coerce them into one `done` boolean.

Loop exit meanings stay template-specific: 0 verified, 2 unverified cap, 3 stall/verify-fail stop, 4 configuration/precondition hold. One-pass/CLI exit 2 is not necessarily cap. Preserve the exit **and** observed reason; provider parsing/prerequisite failures must not masquerade as repair outcomes.

First-pilot proposal, **not a universal loop policy**: one TASK-004 invocation, two repair-fixture pairs, at most three host-agent CLI invocations per repair arm, and one expected-hold pair with zero dispatch, hence at most `1 + 2 × 2 × 3 = 13` host-agent invocations. This is not a bound on provider requests/internal tool turns. Human-approved per-call and total time/cost limits, and the host's enforcement of nested remaining budget, are required separately. If the host cannot enforce them, the model arm is not ready. Fixture classes: one independently checkable fix, one content-progress case, one version/precondition hold, selected independently of the skill's content (fixtures are drawn from an existing corpus or seeded by someone who did not write the skill text). Only the first two belong in the repair denominator. One run per arm cannot damp model nondeterminism — results are directional single-case evidence, not a "fair" estimate of effect size. None is an MR-3 real-world failure or a recurrence sample merely because the model ran.

Fair-comparison controls (a bound on interpretation, not a guarantee of fairness): identical task inputs/oracles, host protection, configured model/version/profile, call/time/cost caps and start-state; fresh contexts and alternated arm order — two pairs cannot separate an order effect from a fixture-order interaction, so order is reported, not claimed canceled. Never remove sealing, sink isolation, required host preflight or acceptance protection from the control. Treatment may differ in skill guidance, generated workflow/navigation and inspectable ledger; report those factors rather than attributing a multi-factor result solely to prose. A stub arm proves control flow, not model utility. A blinded deterministic scorer evaluates the final candidate only, not an arm label or the arm's full artifact set. An unmet provider prerequisite means blocked; do not retry every pair against that prerequisite error. A returned but invalid model proposal is a model/task outcome, not automatically an environment blocker.
